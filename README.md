# 共享自习室预约服务

## 虚拟面试要求

本次面试必须在同一个 Fork、同一个分支中完成，并连续录制一段 30–60 分钟的视频。

视频必须始终包含完整桌面、候选人的摄像头画面、清晰的声音和持续可见的系统时间。所有与作答有关的操作都必须出现在录像中。录像不得剪辑、暂停或倍速处理，也不得使用未录制的设备完成部分工作。

录像开始时，请展示系统时间、Fork URL、当前 Git 分支、起始完整 commit ID，以及干净的 `git status`。

编写代码和运行测试必须由候选人在 GUI IDE（如 IntelliJ IDEA、Eclipse 或 VS Code）中亲自完成，调试必须使用 GUI Debugger。发送请求时建议使用 Postman 或 IDE HTTP Client 等 GUI 工具。可以使用 `curl`、`git` 等命令行工具，但执行前必须说明命令用途和每个参数的含义。

## AI 使用与个人责任

本次面试允许使用 AI 对话工具、IDE 插件或 CLI Agent，但所有 AI 交互都必须出现在录像中。

AI 只能用于分析和提供建议，不得直接修改项目文件，也不得代替候选人完成编码、调试、测试或 Git 操作。使用 Agent 时，候选人必须明确要求它保持只读，不直接执行这些任务。

每次 AI 给出回复后，候选人必须先完整阅读，再继续操作，并对准备采用的建议逐项判断。AI 提到的关键技术概念或方案，候选人需要立即用自己的话说明它是什么、为什么适用于当前问题，以及可能带来的影响。不能解释的内容，不视为候选人已经掌握。

参考 AI 建议完成代码后，必须最小化所有 AI 窗口，回到 IDE 自行打开相关文件，用鼠标指出关键代码，并独立说明：

- 每处修改解决了什么问题
- 关键代码每一行的实际作用和修改原因
- 如何通过测试或运行结果证明修改正确
- 删除或改回一处关键代码后，程序行为会怎样变化

逐行朗读 AI 输出不算解释。对 AI 输出不加判断地全盘接受、照搬或照读，且不能独立解释和验证，将直接视为本次作答无效。

## 准备与运行

请在录像前完成 GitHub 账号注册、仓库 Fork 和 Clone、依赖下载、IDE 安装及项目导入。需要准备 JDK 17 或 21、Git、支持 Java GUI Debugger 的 IDE，以及发送 HTTP 请求的工具。可以使用 GitHub noreply 邮箱，避免在公共仓库中公开个人邮箱。

可以使用以下命令确认环境可用：

```shell
# macOS, Linux, Git Bash or WSL
./mvnw test
./mvnw spring-boot:run

# Windows
.\mvnw.cmd test
.\mvnw.cmd spring-boot:run
```

应用默认监听 `http://localhost:8080`。

## 工程范围

工程只有两个业务实体：`Room` 表示共享自习室，`Booking` 表示某个自习室的预约时间窗口。

所有时间均为同一固定日期的本地时间。本题不考虑时区、周期预约、参与人、容量、取消、权限、认证、并发或外部数据库。

| Room | Booking | Start | End |
|---|---|---|---|
| `room-101` | `booking-1011` | `2030-01-15T09:00:00` | `2030-01-15T09:30:00` |
| `room-202` | `booking-2021` | `2030-01-15T10:00:00` | `2030-01-15T10:30:00` |
| `room-202` | `booking-2022` | `2030-01-15T12:00:00` | `2030-01-15T12:30:00` |

## 面试任务（共四题）

请按顺序完成以下四项任务。每项任务必须形成一个独立 commit，并在 Push 后再开始下一项。不得提前修复后续任务中的故障。

### 每项任务完成后

候选人必须完成以下步骤并作简短说明：

1. 检查完整的 staged diff，确认没有无关文件、构建产物或属于其它任务的修改
2. 最小化 AI，在 IDE 中完成本阶段的总结说明
3. 使用 Conventional Commit 格式提交并 Push

```text
<type>[optional scope]: <description>
```

`type`、`scope` 和 `description` 均使用英文。候选人需要说明 commit message 的含义，以及为什么选择该 type，例如为什么使用 `feat` 而不是 `fix`。

### 一、实现时间窗口规则

实现 `BookingWindowPolicy.evaluate`，按以下顺序返回结果：

1. `start` 或 `end` 缺失：`MISSING_BOUNDARY`
2. `end` 不晚于 `start`：`END_NOT_AFTER_START`
3. 时长短于 30 分钟或长于 120 分钟：`DURATION_OUT_OF_RANGE`
4. 其它情况：`VALID`

30 分钟和 120 分钟均为合法边界。增加单元测试，覆盖上下边界、边界相邻值，以及一个同时违反多项规则的输入。运行一个自选边界测试前，先说明预期结果和判断过程。

完成后按之前的要求 commit。

### 二、修复缺失预约的错误响应

以下请求当前返回 500：

```http
GET /rooms/room-101/bookings/booking-missing
```

它应返回 404，并沿用现有错误结构和 `BOOKING_NOT_FOUND`。响应中不得出现异常类名或调用栈。

修改前，请提出至少三种可能原因，并说明准备如何验证。然后使用 IDE GUI Debugger 单步跟踪，展示 `roomId`、`bookingId`、room 和 booking 的查询结果、实际异常、相关表达式及应用调用栈。根据观察说明哪些猜测得到支持，哪些可以排除。

确认问题后，按以下顺序完成修复：

1. 增加并运行回归测试，确认测试失败
2. 完成最小修改
3. 再次运行测试，确认测试通过

最后说明为什么这里应返回 404 而不是 400，并举例说明其它常见 4xx 状态码的使用场景。

完成后按之前的要求 commit。

### 三、修复可用性判断故障

以下请求与 `booking-2021` 重叠，应返回 `{"available":false}`，但当前实现错误地返回 `true`：

```http
GET /rooms/room-202/availability?start=2030-01-15T10:15:00&end=2030-01-15T10:45:00
```

修改前，请提出几种可能原因，并说明准备如何区分它们。然后使用 IDE GUI Debugger 单步跟踪，展示请求参数、处理到的 bookings、相关子表达式、状态变化和应用调用栈，并使用 Evaluate Expression 或同等功能验证判断。

确认原因后，先增加并运行多个回归测试，允许看到测试失败，并逐一说明每个测试验证的行为；再完成最小修改，运行针对性测试和完整测试，确认全部通过。

最后口头回答一个扩展问题，不需要继续修改代码：假设线上系统使用关系型数据库保存预约数据，某个 room 已有数十亿条 booking，当前实现可能会有什么问题？你会如何优化？

完成后按之前的要求 commit。

### 四、实现创建预约接口

实现：

```http
POST /rooms/{roomId}/bookings
Content-Type: application/json

{
  "start": "2030-01-15T10:00:00",
  "end": "2030-01-15T10:30:00"
}
```

要求：

- 服务端生成 booking ID
- 成功时返回 201、创建后的 booking，以及可以查询该资源的 `Location` 响应头
- 时间窗口非法时返回 400 和 `INVALID_BOOKING_WINDOW`
- room 不存在时返回 404 和 `ROOM_NOT_FOUND`
- 与同一 room 的已有 booking 重叠时返回 409 和 `BOOKING_CONFLICT`
- 时间窗口使用半开区间 `[start, end)`，首尾相接不算重叠
- 失败请求不能新增或修改 booking

增加成功、异常和边界测试。除了状态码，还要验证响应体、保存后的状态，以及失败请求没有修改数据。使用真实请求验证创建成功，并沿 `Location` 响应头查询新资源。

最后口头说明为什么选择 POST 而不是 PUT 或 PATCH，比较它们的 REST 语义和幂等性，并说明其它常见 HTTP 方法的用途。

完成后按之前的要求 commit。
